# KDownloader Agent Guide

Last reviewed: 2026-09-03

This file is the current engineering contract for the extension. Historical release notes live in `changelog/`; do not append dated entries here.

## Project Shape

This repository is a monorepo containing KDownloader and TrueDown. KDownloader is a dependency-free Chrome Manifest V3 extension. Runtime code is plain JavaScript and CSS; background code uses ES modules and the content/page scripts are load-order-sensitive classic scripts.

```text
background/             MV3 service-worker modules and RPC handlers
content/                site actions, shared content helpers/UI, route watcher
shared/                 canonical UI component runtime, i18n, page primitives, icons
popup/                  minimal daily-use popup and search helper
settings.html/.css/.js  advanced options page
injected/               page-context creator-cache bridge
icons/                  extension icons
tests/                  Node test runner and Python migration tests
tools/                  clean build and changelog selection scripts
changelog/              dated release notes and historical archive
manifest.json           permissions and content-script order
truedown/               TrueDown Go application, embedded web UI, Windows resources, tests, and build script
```

Do not edit `dist/` by hand. It is generated and ignored.

## Background Contracts

- `background/constants.js` is the only source for `CONFIG`, storage keys, `API`, and `PAW`.
- `API.HOSTS` contains only hosts that use the shared `/api/v1` and creator override flows. `API.COOMERFANS_ORIGIN` is separate. `PAW` is fixed to `pawchive.pw` and `file.pawchive.pw`; do not reintroduce old Pawchive domains.
- `background/messages.js` builds the RPC table from `background/handlers/*.js` and dispatches only own, string-named function entries. Privileged settings/history operations accept extension-page senders only, while content operations validate the sending document against the supported HTTPS hosts. Long download operations acknowledge synchronously with `{ accepted: true }`, deduplicate bounded request IDs per sender/action, then broadcast progress and a terminal completion message carrying the request ID.
- `background/network.js` owns fetch, cookies, response-size limits, request timeouts, Pawchive bridge routing, Cloudflare/WAF detection, and challenge notifications. API requests are HTTPS allowlisted; Pawchive JSON requests go through `fetchPawchiveJson`.
- `background/db.js` owns IndexedDB history version 3. The active generation pointer and generation metadata make import commit and stats O(1). Export sessions carry that pointer's generation and revision; every page validates both in the same IndexedDB transaction and must fail for a full retry if history changes mid-export. Records use compound identity `[source, service, userId, postId]`; supported statuses are `partial`, `complete`, and `empty`.
- History is not copied through a single runtime message. Use `db.import.begin/chunk/commit/abort` and `db.export.begin/page` with bounded payloads. Export pages carry the generation and revision returned by `db.export.begin`; any intervening history write must abort the export so the user can retry a coherent snapshot. History and creator-flag lookup keys are encoded tuples rather than delimiter-concatenated strings. Duplicate identities must abort an import without changing the active generation. Retired generations and abandoned imports are reclaimed after their safety windows.
- `background/download.js` owns task construction, trusted media-host validation, batching, bounded workers, retries, progress, backend dispatch, and link TXT declaration. Project-file suffix rules are not applied to ordinary site media; they are synchronized for optional TrueDown Dropbox expansion only. Site cookies and full post referrers may be forwarded only to the same trusted site family. Native Chrome fallback is only offered after the persisted, user-confirmed total-failure notification.
- `background/config.js` owns backend, download-rule, external-link filter, Watch, and Gist defaults/normalization. External-link filtering defaults to a user-editable domain blacklist containing `patreon.com` and matches subdomains. Download backends are loopback-only (`localhost` or `127.0.0.1`). The optional AB-compatible API Key is empty by default and, when set, contains 32-256 printable ASCII characters with no surrounding whitespace. It lives in local-only extension storage, and browser cookies for the TrueDown dashboard are never used as backend credentials. `settings.restoreDefaults` resets those values, disables the creators override, and reschedules the Watch alarm; it never clears history or the Watch list.
- `background/creators.js` owns the Kemono/Coomer creator cache and enable flag. The injected cache bridge must honor enable/disable changes immediately. `background/watch.js` owns Pawchive Watch only and bounds high-concurrency checks.
- Remove exports only after `rg`/`git grep` confirms there are no runtime, test, or build references.

## Content Script Order

Keep `manifest.json` injection order stable. The current order is:

1. Pawchive document-start API bridge: `content/paw_api_bridge.js`.
2. Kemono/Coomer document-start page injector: `content/injector.js`.
3. Site UI scripts: `content/helpers.js`, `shared/i18n.js`, `shared/components.js`, `content/ui.js`, `content/download.js`, `content/router.js`, then the site action script.
4. Favorites pages: `helpers -> i18n -> components -> ui -> router -> flag/index.js`, plus `content.css`.

The site action scripts are `actions.js`, `paw_actions.js`, and `coomerfans_actions.js`. They discover site-specific DOM data and request payloads; shared creation, state, modal, and progress behavior belongs in `content/ui.js` or `content/download.js`.

- Register idempotent renderers with `KDRouteWatcher`. Do not patch history or create a second bootstrap scheduler.
- Use `safeSendMessage`, batch status checks with `checkDownloadedMany`, and guard async renders with `isRenderCurrent`.
- Kemono, Pawchive, and CoomerFans controls use the shared `kd-ui-action` Shadow DOM host with an internal native `button`. Create and recover action and external-link-dialog hosts only through their `KDComponents.create*Element` and `KDComponents.ensure*Element` factories; direct `document.createElement` calls may leave an unverified host in an isolated content-script world. Creator actions carry `variant=creator`, `data-batch-download="true"`, and `data-path`; Favorites flags carry `variant=flag`. Do not add legacy button classes, a second injected-control implementation, or inline positioning styles.
- Pawchive Watch is available only on creator pages. Its state is read and changed through `watch.*` RPCs.
- Pawchive posts with `has_full=false` must never create media tasks or history records, but any valid HTTP(S) links already present in their bounded post content are still filtered, returned, and shown. An `empty` history status remains handled for batch deduplication, while direct post and creator-card actions remain manually retryable so link-only or later-updated posts can reopen their links.
- History source identities must never fork beyond exactly two namespaces: CoomerFans uses `source=coomerfans`; Kemono, Coomer, and Pawchive share `source=default`. Never add or persist a Pawchive-, Kemono-, Coomer-, host-, or route-specific history source. Pawchive routing is derived from the trusted sender/origin, never from history identity. Compatibility reads may normalize the briefly emitted legacy `pawchive` label directly to `default`, but must not preserve it as a third namespace.
- The document-start bridge accepts only same-origin Pawchive `/api/v1/` GETs. Never pass Cloudflare clearance cookies, browser identity headers, arbitrary methods, or arbitrary origins through messages.

## Shared UI Rules

- `shared/components.js` is the canonical cross-product component runtime. Its action and links-dialog factories use native Custom Element upgrades when available and imperatively hydrate the same Shadow DOM when isolated-world nodes remain unupgraded. They guard constructable-stylesheet adoption and audit connected action visuals and cursor state with a Shadow-root style fallback. Popup, settings, and content scripts load it directly; `truedown/web/components.js` is a generated byte-for-byte mirror maintained by `npm run ui:sync` and verified by `npm run ui:check` and the TrueDown build.
- `shared/ui.css` is the single source for extension-page tokens, controls, panels, focus rings, notifications, loading indicators, segmented controls, and reduced-motion behavior.
- `shared/ui.js` owns extension-page message sending and re-exports the canonical component helpers through `KDUI`. Busy-button state, toast lifecycle, progress rendering, icon-button updates, and segmented state belong to `shared/components.js`; page scripts must not reimplement them.
- `shared/icons.svg` is the only extension-page icon sprite. Use external `<use href=".../shared/icons.svg#icon-name">`; do not duplicate inline symbol blocks.
- Use the `kd-*` component vocabulary (`kd-panel`, `kd-button`, `kd-icon-button`, `kd-input`, `kd-select`, `kd-hidden`, etc.). Page CSS should define layout only.
- The Chrome action popup width is explicitly owned by `popup/popup.css`. Preserve the configured project value unless the user requests a width change; verify the real extension popup after changing it.
- Settings uses the same primitives and a normal-flow sticky action bar; controls must not cover other content.
- `content.css` is host-safe and layout-only. It authoritatively pins the size, position, pointer hit area, and cursor of `kd-ui-action` hosts because Shadow DOM cannot isolate the host box from site CSS. Injected visuals, state animations, and modal styling belong to the `kd-ui-action` and `kd-ui-links-dialog` Shadow DOM definitions in `shared/components.js`; never add a parallel light-DOM visual implementation, generic `spin`/`fadeIn` names, or `transition: all`.
- Use explicit motion durations and honor `prefers-reduced-motion`. Keep cards and modal corners at 8px or less. Do not introduce decorative blobs, gradients, or one-note color palettes.
- Every interactive icon needs an accessible label/title; decorative SVGs must be `aria-hidden` and unfocusable. Dynamic status buttons must update `aria-busy`, `aria-disabled`, and `aria-label` where applicable.
- External-link modals must deduplicate and accept only HTTP(S) URLs, expose dialog semantics, close on Escape/backdrop, trap focus, and restore focus.
- Keep host-page positioning changes class-based, not inline `style` assignments. `ensurePositionContext` preserves an existing non-static position, adds `kd-position-context` only to static containers, and pairs it with `kd-overlay-container`; stale and route-cleanup removal must release both classes after the last overlay action leaves.

## Popup And Settings Behavior

- Popup defaults to Pawchive Site Search and supports Pawchive, Kemono, Coomer, and CoomerFans URL shapes from `popup/search.js`.
- Creator Fetch exposes non-persistent `default`, `full`, `links`, and Pawchive-only `dms` modes. Links and DMs modes may run without a media backend and declare their TXT directly through `chrome.downloads`; DMs scrape only the creator's fixed Pawchive `/dms` HTML page and export published dates, text, and links without history writes.
- Popup shows Creator Fetch and History by default; Search Cache and Gist panels are visibility-controlled by their settings. Destructive history maintenance remains in settings.
- Popup global progress is hidden when `total <= 0` and visible only for active work.
- Settings uses RPCs for every persisted setting. Do not write `chrome.storage` directly from page scripts. Restore defaults preserves IndexedDB history and `pawchiveWatches`.

## Storage And Configuration

Current durable keys are `backendConfig`, `backendSecrets`, `downloadRulesConfig`, `externalLinkFilterConfig`, `watchConfig`, `gistConfig`, `gistSecrets`, `creatorsOverrideEnabled`, `pawchiveWatches`, `pawchiveWatchIcons`, and lightweight progress/revision signals. Backend and Gist tokens live only in the local secret keys and are omitted from sync storage. Download history is IndexedDB; pending native fallback tasks use session storage.

Download rules are stored in sync storage as `{ enabled, excludedExtensions, syncToTrueDown }`. They configure the default choice and suffix list for optional TrueDown Dropbox expansion; they do not filter ordinary KDownloader media tasks. Values are lowercase dot-prefixed suffixes and matching is case-insensitive against normalized filenames, then URL paths. The default selectable list is `.psd`, `.clip`, `.sai`, `.sai2`, `.kra`, `.xcf`, `.procreate`, `.afphoto`, `.afdesign`, `.blend`; TrueDown synchronization is enabled by default and occurs only when the settings page saves the rules.

Pawchive Watch stores `{ schemaVersion: 1, watches }` in local storage and keeps avatar data outside exports. A manual add establishes the current profile update baseline before notifications are enabled. Scheduled checks aggregate updates/failures and preserve baselines on failure.

## TrueDown Runtime

- TrueDown keeps native form controls in Light DOM and consumes the generated canonical component runtime for shared behavior. Go cannot embed the parent `shared/` directory, so release builds fail rather than accept a stale `truedown/web/components.js` mirror.
- Packaged Windows builds use the GUI subsystem, embed a Per-Monitor V2 DPI manifest with the legacy per-monitor fallback, and run as a single tray application per resolved data directory. The tray thread explicitly keeps that DPI context so its icon, native menu metrics, and physical coordinates follow the taskbar monitor when scale factors differ. A second launch opens the existing dashboard without starting another aria2 manager. The tray owns dashboard, downloads, application-log, and graceful-exit actions; closing the browser never stops TrueDown. Managed aria2 and helper processes must not create console windows.
- Linux and macOS builds are foreground browser-dashboard services. They keep the same application log and authenticated dashboard lifecycle, support confirmed exit through `POST /system/exit`, handle `SIGINT`/`SIGTERM`, and enforce one process per resolved data directory with a non-following lock file. Linux uses the XDG data directory (falling back to `~/.local/share/truedown`); macOS uses `~/Library/Application Support/TrueDown`.
- TrueDown writes application events to `truedown.log` in the data directory, rotates at 4 MiB with three backups, and never treats the browser as the log owner. `GET /system/logs` returns only the newest bounded 256 KiB through the authenticated HTTP boundary. The dashboard may render and copy that text only with text-safe DOM APIs; API keys, request headers, and secret-bearing task payloads must never be logged.
- TrueDown listens on `127.0.0.1:15151` by default. A non-loopback `TRUEDOWN_ADDR` requires `TRUEDOWN_ALLOW_REMOTE=1` and must name a specific interface; wildcard binds are rejected.
- Windows packages and launch fallbacks use the reviewed bundled stable aria2. Linux and macOS resolve a regular executable from a packaged `aria2c`, `TRUEDOWN_ARIA2_PATH`, the system `PATH`, or standard Homebrew locations. Aria2 Next is currently Windows-only and optional, stored as a versioned file under the data directory, and can be installed, updated, selected, or deselected only through explicit, separate dashboard actions; installation never changes the saved engine preference. NEXT downloads use only the latest stable `AnInsomniacy/aria2-next` GitHub Release, require its exact Windows architecture asset and checksum file, and must pass release SHA-256 plus executable version checks. NEXT never follows upstream automatically. Engine selection drains in-flight dashboard requests, stops the old downloader manager, starts the verified target, and restores queued, downloading, and paused tasks from the durable database without restarting the HTTP server; failed target startup restores the previous engine. Unexpected engine exits preserve recoverable task intent and retry the active engine three times before one bounded TrueDown self-reload per recovery incident. Switching from NEXT to stable is rejected while unfinished BitTorrent tasks exist. Invalid saved NEXT files and NEXT startup failures fall back to the packaged stable engine for the current process while preserving the saved preference and reporting the reason. NEXT-only startup options must be gated by the installed engine version.
- Numbered Windows release builds persist program-update settings, verified NEXT metadata, and staged-update metadata in `truedown.updates.json`. TrueDown self-update is enabled by default, checks only numbered stable `truewayd/KDownloader` releases, and requires an exact build-matched release archive and strict update manifest before staging only `TrueDown.exe` under the data directory. Automatic apply waits until queued, downloading, and paused counts are all zero. An external copied helper stops aria2 with the parent, preserves `TrueDown.exe.previous`, waits for a per-update startup health token, and rolls back on failure; it never replaces either engine, task data, or configuration. Development builds cannot self-update.
- TrueDown implements AB Download Manager's HTTP browser-integration fallback on the same listener: `POST /ping` returns `pong`, and `POST /add` accepts bounded HTTP download batches from the official extension. It maps each item's link, suggested name, headers, and download page into the normal TrueDown queue; HLS items are rejected because aria2 does not provide AB's HLS download behavior.
- API Key authentication is disabled by default and is persisted in `truedown.auth.json` when changed from the dashboard. Keys use the same 32-256-character printable-ASCII, no-surrounding-whitespace contract as KDownloader. Enabling it creates or reuses `truedown.token`, returns an authenticated session in the same settings response so the UI remains connected, and makes the KDownloader API Key field mandatory only for that TrueDown instance. Loopback dashboard session cookies carry a base64url encoding of the key while `X-Api-Key` keeps the exact raw value. `TRUEDOWN_REQUIRE_TOKEN=1` or `TRUEDOWN_API_TOKEN` manages the setting externally.
- A non-loopback TrueDown listener also requires `TRUEDOWN_TLS_CERT`, `TRUEDOWN_TLS_KEY`, and enabled token authentication. Remote listeners lock the dashboard toggle on; remote dashboards ask for the token and keep it only in the current tab's session storage.
- The HTTP boundary validates request hosts and write origins, applies security headers and timeouts, limits start requests to 1 MiB, accepts exactly one known-field JSON object, and returns task snapshots without headers or aria2 options. `GET/POST /settings/download-rules` persists the bounded Dropbox mode and filter defaults; filter-only posts from older KDownloader clients preserve the current mode. `GET/POST /settings/runtime` persists aria2-wide concurrency and aggregate download-speed limits; posts from older dashboard clients that omit the speed field preserve its current value. `GET/POST /modules` lists or changes resolver enablement. `POST/DELETE /modules/package` imports a package of at most 64 KiB or restores its embedded baseline. `GET /system/logs`, `GET /system/update`, `GET/POST /settings/updates`, `POST /system/update/check`, `POST /system/update/restart`, `POST /system/engine/next`, `POST /system/engine/select`, and `POST /system/exit` expose bounded diagnostics and program/engine lifecycle without accepting client paths or release URLs. Start requests carry bounded, module-owned options under `moduleOptions`. KDownloader never repeats filter rules inside ordinary task requests. KDownloader, AB's extension, and the TrueDown dashboard all use the same `X-Api-Key` authentication header.
- TrueDown reads persistent JSON configuration through bounded regular-file reads and writes it with same-directory, synchronized atomic replacement and crash-backup recovery. Resolver packages, auth, runtime/download-rule settings, tracker-research state, and updater state must not bypass that boundary.
- Download URLs are absolute HTTP(S) URLs without embedded credentials. Output names, headers, folders, queue IDs, and aria2 options are bounded; process hooks, RPC controls, and local-file aria2 options cannot be overridden through `extraArgs`.
- The manager indexes aria2 GIDs for status polling, clears drained queue references for GC, and exposes UI snapshots instead of cloning secret-bearing task payloads on every poll.
- TrueDown admits at most 256 queued/active tasks to aria2 at once, persists polled state outside the task lock in revision-guarded batches, and exposes bounded, filename/link-searchable task pages with summary counts and ETags. Unchanged searched or sorted task pages are rejected from revision validators before their global result is rebuilt. Explicit task-page sorting is server-side across the filtered result and supports ID, file name, status, link, and progress in either direction. aria2's simultaneous-download limit and aggregate download-speed limit are persisted in `truedown.settings.json`; concurrency defaults to 3, speed defaults to unlimited, and both apply immediately through aria2 global options via the runtime settings API. The dashboard renders 100 tasks per page, can pause/resume the whole queue, and uses operations bounded to 1,000 explicit task IDs for pause, resume, retry, and record removal; "retry all" drains multiple bounded batches. Host path-opening endpoints accept no client path: directory actions resolve the configured default or a task ID, and file opening resolves only a completed task ID to its regular direct-child output. Removing a completed task skips confirmation and preserves its downloaded file. Destructive confirmations and remote API Key entry use the dashboard's accessible custom modal, never browser dialogs. Removing an aria2-confirmed active task stops it and safely removes its direct-child partial data and `.aria2` control file before deleting the record. Retrying Aria2 Next's exact stale HTTP byte-range error requires dashboard confirmation and removes only that task's validated direct-child partial data before starting from zero; all other retry paths preserve resume data.
- The experimental tracker-research module is compiled in but disabled by default and requires an explicit dashboard risk confirmation plus an active Aria2 Next engine exposing `aria2.replaceBtTrackers` (official releases v2.5.7 or newer). Its status identifies the active engine/version and RPC requirement; the dashboard must block first-time enablement when support is known to be unavailable. It rewrites only HTTP/HTTPS tracker entries to opaque, automatically allocated `127.0.0.1` relay URLs, leaves UDP trackers unchanged, accepts only token-bound GET tracker queries containing `info_hash`, and never acts as a general proxy. HTTPS forwarding uses ordinary upstream certificate validation and no MITM CA. The RatioGhost-compatible leecher threshold, multiplier ranges, random bonus, zero-download, and seed-simulation settings plus restorable original tracker lists persist in owner-only `truedown.tracker-research.json`; acknowledgement is never persisted, and API status never exposes tracker URLs, passkeys, info hashes, tokens, or the internal port. `GET/POST /settings/tracker-research` owns this lifecycle, and module updates follow TrueDown rather than an independent updater.
- Aria2 Next-only BitTorrent creation uses `POST /start-bt-download` and accepts exactly one bounded local `.torrent` payload, magnet, or HTTP(S) torrent URL. Imported metainfo remains in the secret-bearing durable request identity for restart resubmission but is omitted from task snapshots. The user-selected directory is the native torrent save root: single-file torrents write directly there and multi-file torrents retain their torrent-named root, with no `out` override or user-facing folder-mode switch. NEXT runs with `<data-dir>/aria2-next-state`, integrity checking, and one-second BT resume saves; restored tasks attach to an existing native GID or resubmit with the same GID, and HTTP torrent metadata parents persistently rebind to their `followedBy` BitTorrent child. Official NEXT owns the libtorrent tracker User-Agent, extended-handshake client string, and `A2` peer fingerprint; retired aria2 `peer-agent` and `peer-id-prefix` inputs must not be presented as effective settings. TrueDown surfaces the actual engine-owned identity and zero-speed peer/seeder/tracker/availability counters. NEXT v2.6.5 and newer writes bounded rotating native debug diagnostics to `<data-dir>/aria2.log`; older engines retain the summarized console log.
- Dropbox and Google Drive use versioned resolver engines behind the same registry. Both have embedded declarative baseline packages and are enabled by default, while `truedown.modules.json` stores enablement and the data directory's `modules/<id>.json` files store independent updates. Package schemas and engine IDs are strict, versions only move forward from the current baseline/active version, invalid persisted updates fall back to the baseline, and dashboard import/reset atomically swaps immutable module snapshots without restarting or mutating in-flight calls. Packages may change only module-approved paths, cookie names, and request identity values; trusted hosts and resource limits remain compiled into TrueDown. Disabling a module stops it from claiming new dashboard, start-API, or AB-integration links; existing tasks retain their persisted module ID and may still refresh or resume safely. Module option decoders reject unknown fields, and unknown module IDs never reach a resolver.
- The Google Drive module supports exact HTTPS `drive.google.com` and `docs.google.com` public file, native document, and folder URL shapes. It normalizes file IDs to stable `/uc` links, handles bounded large-file confirmation pages, exports Docs/Sheets/Slides with bounded format choices, and recursively parses `embeddedfolderview` with directory, depth, response-size, and file-count limits. Temporary trusted Google content URLs and confirmation cookies are refreshed immediately before aria2 admission and are never persisted as the task identity. Google redirects are HTTPS allowlisted, resolved traffic follows the configured system proxy, and private account login automation is not provided. The protocol behavior is independently implemented in Go with attribution to gdown's MIT-licensed public-link flow.
- Public Dropbox `/scl/fo/` folder submissions default to direct archive download, but the TrueDown general settings may persist `dropboxMode` as `direct` or `expand` in `truedown.download-rules.json`. The dashboard initializes each new-task form from that value, and browser-integration or start-API requests that omit a mode use it automatically; an explicit per-request mode still wins. Each request may independently choose whether the persisted suffix list applies. Expansion stays entirely inside TrueDown without Chrome or a Developer API token: the isolated adapter establishes an anonymous CSRF session, derives the current `secure_hash`, calls `list_shared_link_folder_entries`, follows signed vouchers, traverses sibling folders with bounded parallelism, then bulk-adds all accepted stable `dl=1` tasks while preserving hierarchy and duplicate/resume behavior. KDownloader can synchronize the suffix list without resetting TrueDown's independently chosen mode. Neither frontend calls or parses Dropbox. The private web protocol is intentionally isolated because Dropbox may change it.
- Each expanded Dropbox file resumes independently. Failed `dl=1` tasks with an existing partial file and `.aria2` control file may accept a renewed shared URL for the same folder and file name. TrueDown probes the current trusted content URL to compare the persisted remote name, total length, and any available Digest hash, but gives aria2 the stable file sharing URL so aria2 obtains a fresh redirect instead of reusing a possibly single-use content URL. Dropbox refresh and content traffic honor matching `HTTP(S)_PROXY` environment variables first and otherwise use the current Windows user proxy; the resolved proxy is passed to aria2 per task while loopback RPC traffic stays direct. Legacy `/sh/` archive links retain the bounded archive fallback.

## Build And Release

- `manifest.json` is the single source for KDownloader's three-component `MAJOR.MINOR.PATCH` product version. Bump it deliberately for user-visible releases: major for incompatible changes, minor for backward-compatible features, and patch for backward-compatible fixes. Do not duplicate the product version in `package.json` or another source file.
- `tools/read-extension-version.ps1` validates and returns that product version. `tools/build-extension.ps1` creates a clean unpacked directory (normally `dist/KDownloader`) containing runtime files only; release builds append the bounded GitHub run number as Chrome's fourth numeric version component and add a display-only `version_name` in the staged manifest. It rejects invalid versions, Python artifacts, underscore-prefixed reserved paths other than `_locales`, and reparse points in runtime inputs or recursively cleaned output trees.
- KDownloader release archives, artifact names, tags, and release titles include both the product version and monotonic build number. A checked-in manifest version must never remain at a placeholder such as `1.0.0` across unrelated releases.
- `package.json` is developer-only metadata (`npm test`, `npm run test:python`, `npm run version:check`, and `npm run build`) and is not copied into the extension build.
- Product-specific release notes are required in `changelog/kdownloader/YYYY-MM-DD-NNN-short-slug.md` or `changelog/truedown/YYYY-MM-DD-NNN-short-slug.md`. Changes affecting both products require one note in each directory. Increment the zero-padded daily sequence; `tools/read-latest-changelog.ps1 -Product KDownloader|TrueDown` selects the newest dated non-reparse-point note for that product and writes `release-notes.md` without following a reparse-point input or existing output.
- `.github/workflows/publish-extension.yml` builds, archives, uploads, and publishes a release whose body is read from that latest changelog file. Keep the filename date prefix sortable and do not rely on GitHub-generated notes for project changes.
- KDownloader and TrueDown releases are path-scoped. KDownloader changes publish through `publish-extension.yml`; `truedown/**` changes publish through `publish-truedown.yml`. A commit that changes both products publishes both releases.
- `truedown/build.ps1` accepts output only under `truedown/dist/`, rejects reparse traversal in inputs and recursively cleaned outputs, injects the release version, monotonic GitHub run number, and commit into the Windows GUI-subsystem `TrueDown.exe`, then creates the Windows package with only `TrueDown.exe`, the stable `aria2c.exe`, `ARIA2_COPYING`, and the third-party notices. The build verifies the PE subsystem, linked icon, and exact embedded DPI manifest. TrueDown tags use the `truedown-build-*` prefix so they cannot collide with KDownloader tags. `publish-truedown.yml` publishes the exact tested commit as `TrueDown-build-<run>.zip` plus `truedown-update-<run>.json`; release actions are immutable-SHA pinned, and the strict manifest binds product, repository, version, build, archive name, size, and SHA-256. The release body comes from the latest dated changelog.
- `truedown/build-unix.sh` creates fixed-path Linux `amd64`/`arm64` packages and macOS `.app` bundles with CGo disabled. Linux packages include a desktop entry and SVG icon; macOS bundles include the generated multi-resolution ICNS. Unix release publication, macOS code signing/notarization, and a native menu-bar controller remain separate release work.
- Windows builds embed the multi-size TrueDown application icon from `truedown/windows/truedown.ico` through the checked-in amd64 PE resource object. The source icon is derived from the canonical web logo by `truedown/windows/generate_icon.ps1`, which also creates the macOS ICNS; release builds must verify the PE group icon at resource ID 2 used by the tray as well as the Explorer-associated icon, without regenerating or downloading build tools.

## Verification

Run the focused test first, then the full suite:

```text
npm run ui:check
npm test
python -m unittest tests/migrate_history_json_test.py
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/build-extension.ps1
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/read-latest-changelog.ps1 -Product KDownloader -OutputFile release-notes.md
cd truedown
go test ./...
go vet ./...
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/prepare-wsl-tests.ps1
wsl -d Ubuntu -- bash tools/run-linux-tests.sh dist/wsl2/tests
wsl -d Ubuntu -- bash tools/smoke-linux.sh dist/wsl2/TrueDown
```

When UI or content code changes, also verify:

- the real Chrome action popup in both color schemes, preserving the configured width;
- settings at desktop and mobile widths with no horizontal overflow or action-bar overlap;
- Kemono, Pawchive, CoomerFans, and Favorites reinjection after history navigation/HTMX swaps;
- keyboard focus, reduced motion, loading/progress, success/error/reset states, modal focus trapping, and duplicate-render idempotency;
- backend slow/failure paths, native fallback confirmation/cancellation, and absence of premature history writes.

## Editing Rules

- Prefer async/await, structured parsers, centralized network/download/DB boundaries, and small focused modules.
- Use `apply_patch` for manual edits. Keep comments short and explain only non-obvious logic.
- Preserve unrelated user changes in a dirty worktree. Never reset or checkout files to discard work you did not make.
- Keep new files ASCII unless the existing file format requires another charset.
- Update `manifest.json`, this guide's current contract, tests, and a dated `changelog/` file whenever a change affects runtime APIs, injection order, permissions, storage, or release behavior.
